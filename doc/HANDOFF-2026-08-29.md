8. `pi_end_of_dma_event` no longer calls `dd_update_bm` (BM advances via timed DD_BM_INT events only, matching parallel-n64).

## UPDATE 4 — NEW FINDINGS (session 2026-08-26 continued)
### C2S buffer handler added to `dd_dom_dma_read`
- Missing handler for `MM_DD_C2S_BUFFER` (0x05000000) identified: `__osLeoInterrupt` does a second PI DMA from `LEO_C2_BUFF` to `blockInfo->C2Addr` (`&LEOC2_Syndrome[0]`). Without a handler, it hit "Unknown DD dma read" error path.
- Added C2S buffer handler: copies from `dd->c2s_buf` to RDRAM with `^3` byte-swap on source, returns early, invalidates R4300 cache.
- **Reverted DS buffer direction fix**: The fall-through copy `mem[cart_addr] = dram[dram_addr]` (RRAM→device) is technically backwards for a DMA read, but changing it to device→RRAM caused a regression (black screen from start, no boot at all). The original upstream direction has been working for boot — the game may read the DS buffer via memory-mapped I/O rather than PI DMA, making the dd_dom_dma_read DS path dead code.
- **`__osLeoInterrupt` cmdType==2 issue**: After C2 DMA completes, handler returns without calling `__osLeoResume()`. For track mode (2 blocks), `__osLeoResume()` IS called after first block's C2 DMA. For non-track mode, the `leointerrupt` thread hangs. Game likely always uses track mode.
